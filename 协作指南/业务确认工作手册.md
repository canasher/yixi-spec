## 一、使用方法与主版关系

[待确认事项](../维护记录/待确认事项.md)继续作为问题总表，保留问题-01～问题-14、影响范围、负责人和关闭证据。本手册是这些问题的业务讨论入口，不是第二份业务规则主版。

每个问题按“先理解场景 → 查看已有推荐 → 调查真实做法 → 比较选择及影响 → 记录结果 → 回写正式规则”的顺序处理。不能只写“需要”“支持”“可配置”或“以后再说”。

文中严格区分三类内容：

- **已有依据**：当前仓库中已经写明的方向或推荐；推荐仍需采纳，不因出现在本手册而生效。
- **本稿建议**：本次提出的讨论方法、问题拆解和材料要求；不是行业统一标准，也不是新增批准规则。
- **现场待查**：只能由实际客户、洗涤厂、财务、实施或设备供应方提供的信息；没有材料时如实写“不清楚／待调查”。

产品负责组织业务问题与整理结论；运营、司机、仓管、酒店联系人说明实际作业；经营授权人和财务确认收费、授信、退款、赔偿及责任；研发负责身份、权限、接口、迁移、消息和设备技术方案。具体人员均待项目指定，不由本手册代签。

已明确的先租洗后普洗、一期 RFID、保留原四端一期范围、重建旧测试强业务、复用平台基础，不重新作为开放选择。未来范围不因讨论时被提及就进入一期。

## 三、逐项讨论卡

<a id="Q-01"></a>
### 问题-01：第一批先把哪一段业务做通？

**场景。** 资料很多，但当前开发人员需要知道这一批到底做什么、哪些必须完成、哪些暂时不做。把整包文档标为“确认”会掩盖仍未决定的细节。

**已有依据。** 当前按任务采纳相关规则，不要求先把二三期讨论完；首批从基线、范围、身份和客户服务底座推进。不存在整包业务批准记录。

**请逐项回答。** 第一批服务哪个试点工厂／客户？由哪些角色操作？从什么动作开始，到什么结果算完成？涉及哪几条规则？本批不做哪些入口？哪些参数已有真实依据，哪些只能模拟？

**选择与影响。** 可以先做内部主数据维护，也可以安排包含外部身份的业务切片；后者必须先完成对应身份和授权方案。不要把“主数据能维护”说成“酒店收发已完成”。

**本稿建议。** 先确定一个前后端可共同演示、可验收的小范围，不把十四类全部变成开工前置。产品提供场景和边界，研发拆任务，测试补结果；项目负责人采纳本批范围。

**需要材料／完成证据。** 一张本批范围卡：试点、角色、起止动作、明确不做、规则版本、通过示例、责任人。关联 `TASK-01`；实施前先核对 `TASK-00`。

<a id="Q-02"></a>
### 问题-02：谁可以看什么、做什么？

**场景。** 酒店人员可能只负责一家酒店，也可能代管多家；司机有内部人员和外包人员；无人收脏设备没有员工操作。不能因为知道酒店编号或设备编号就取得权限。

**已有依据。** 现有内部账号能力不等于酒店外部身份已经实现。酒店、外包司机和无人设备仍需正式接入方案，不能用客户字段代替授权。

**请逐项回答。** 谁创建酒店账号？一个人可能管理几家酒店？能否查看价格、欠费、附件和导出？司机只能看自己当天任务，还是能看所有客户？换班后权限如何交接？员工离职、更换外包司机、酒店停用和设备丢失时，由谁立即停权？

**选择与影响。** 单酒店绑定较简单；多酒店绑定有业务价值但需要明确授权范围和审批。司机按分配任务使用，不应为了方便默认开放全部客户。是否允许跨酒店管理是业务选择，具体会话与鉴权方式是研发设计，不让产品选择技术枚举。

**本稿建议。** 产品先填“角色 × 可见数据 × 可执行动作 × 授权人 × 撤销场景”表，再由研发形成安全设计。超出已确认范围的访问不能默认允许。

**需要材料／完成证据。** 去敏的角色实例、权限矩阵、停权案例；研发提交身份方案，测试验证越权和撤权。关联 `PD-018/021/037`、`TASK-02`、原问题表列出的身份验收项。

<a id="Q-03"></a>
### 问题-03：酒店退回布草后，什么时候能再领？

**先解释名词。** 这里的“恢复配额”，是释放这次已经发出、尚未按规则结清的占用，让酒店能够再次申请相应数量；不是增加合同约定的总配额。司机接管实物、工厂实际收到、酒店可再次下单以及损失责任，是相关但不能混为一谈的事实。

**已有依据。** `PD-023` 与 `BR-R008/013` 推荐：默认在有证据的司机交接时恢复；要求更严格的客户可按工厂实收恢复；企业默认可由协议覆盖，本轮保存规则快照。该建议仍待采纳，酒店签收新送来的净品不是本轮回收恢复节点。

**讨论例子（合成数据，不是真实客户政策）。** 假设某酒店某一品项总配额100件，已发未回占用100件，没有其他订单预占，也没有临时增配。上午司机有效交接80件，下午工厂实际确认78件，另2件待查。

| 选择 | 上午交接后可再次申请 | 下午应怎样理解 | 需要接受的影响 |
|---|---:|---|---|
| A：司机有效交接时恢复 | 80件 | 同批工厂复核不能再加78件；差异2件进入调查和受控处置 | 酒店无需等待返厂；必须能证明交接，且明确后续差异责任 |
| B：工厂有效实收时恢复 | 0件 | 确认78件后可申请78件；另2件按未决占用和异常规则处理 | 减少尚未实收就恢复的情况；酒店可能等待返厂，紧急补货需另外授权 |

这里的80件必须是本轮资产明细可追溯的有效交接，不是司机口头填写的数量。差异2件不能仅凭数量差就默认向酒店收费、自动判责或改写历史。任何冲正须按后续事实和批准规则处理。

**产品需要带现场人员回答的问题。**

| 子问题 | 回答提示 | 谁提供事实 |
|---|---|---|
| 03-01 正常恢复节点 | 选择司机交接／工厂实收，或写明本期不启用的理由；不能同时对同一轮释放两次 | 运营、酒店联系人 |
| 03-02 交接如何证明 | 有哪些实际可取得的证据：单件扫描、任务、地点时间、操作人、交接凭证？哪些是必需，缺一项怎么办？ | 司机、实施、仓管 |
| 03-03 司机80、工厂78 | 2件由谁调查？调查期间酒店是否还能领货？结论怎么记录？谁能授权更正？ | 物流运营、业务负责人 |
| 03-04 返厂发现司机漏扫 | 能否确认是哪个资产、哪个未结轮次、原责任酒店和合法收货点？满足哪些条件才自动补收？ | 仓管、实施 |
| 03-05 到工作台才发现漏扫 | 谁复核、看什么证据？哪些例外确实需要自动处理？“扫到了”是否足以说明来源？ | 生产、仓管 |
| 03-06 A酒店资产在B酒店交回 | 原责任酒店如何确认？实际交货酒店如何记录？来源不明时谁处理？ | 司机、运营 |
| 03-07 不同客户不同策略 | 是否真有首客合同差异？按企业默认还是协议覆盖？切换后旧轮次如何保留原规则？ | 产品、业务负责人 |
| 03-08 急需发货但配额未释放 | 是否允许有界临时增配？谁批准、上限和期限是什么？没有授权是否拒绝？ | 业务负责人 |
| 03-09 重复和迟到扫描 | 司机补传、工厂补漏和工作台扫描指向同一轮时，界面怎样说明“已计入”，避免再次恢复？ | 产品、研发、测试 |

**补漏的现有推荐。** 返厂补漏（原B类）有充分证据时可自动确认；工作台补漏（原C类）默认人工确认，只有明确授权且符合条件的白名单才自动。归属、原轮次、位置或时序不明的不直接补；不知道来源的资产先保留观察和异常。补漏不是生成虚假的洗涤或质检记录。

**本稿建议。** 保留当前推荐作讨论起点，先验证首客能否取得可靠交接证据，而不是让产品从零猜哪种更合理。没有证据时不偷换成另一个默认策略，也不以“随便配”结束讨论；记录受阻场景，继续不依赖该决定的工作。

**请收集的材料。** 一次正常收货、一次数量差异、一次漏扫或串店的去敏单据及现场说明；记录谁、何时、在哪、确认了哪些资产。没有发生过某类异常时，可用上面的合成例子讨论，但明确不是现场证据。

**完成证据。** 选定恢复节点、证据要求、补漏条件、差异处理人、客户适用范围、规则生效版本和临时增配授权；正常、漏扫、串店、重复上传及跨策略旧轮次的预期能够由产品、运营和测试说清楚。关联 `PD-005/017/023`、`BR-R008/009/013`、`TASK-06/07`。

<a id="Q-04"></a>
### 问题-04：上线前已经存在的布草和余额怎样登记？

**场景。** 新工厂接入时，部分布草在酒店、部分在厂内，可能有历史欠款和余额；不能只导一个总件数就认为全部可发，也不能把旧测试数据当成真实期初。

**已有依据。** 资产、在外轮次和占用、配额、资金分别需要凭证；初始化支持预览、确认和防重；激活不自动等于净品放行；无证据不补造洗涤次数或余额。

**请逐项回答。** 现有资产能否逐件识别？哪些在酒店、谁确认归属？厂内净品由谁确认可以发？历史余额和欠款以什么账为准？期初时间点如何划定，盘点期间仍收发怎么办？录错后谁能更正？

**选择与影响。** 有完整证据的数据可进入确认流程；资料不完整的部分先列待核，不假装全部准备完成。只录资产不录在外占用可能影响后续配额，资金期初不能由仓管估算。

**本稿建议。** 先选一家试点，实施、仓管和财务实际试填，暴露缺列和证据缺口；将“已登记”“待核对”“可发”分开。人工产出确认要说明证明的是哪项事实，不宣称完成未做过的检测。

**需要材料／完成证据。** 去敏期初样表、盘点时间及来源凭证、预览核对与批准人、重复导入和更正预期。关联 `PD-007/019/024/026`、`TASK-04/08`。

<a id="Q-05"></a>
### 问题-05：怎样才算真正交付完成？

**场景。** 装车100件，酒店只收到98件，或酒店暂时无人确认。车辆到达不等于全部交付，不能用一个“完成”按钮抹掉未交的2件。

**已有依据。** 推荐使用有证据的实际交接，自动交付默认关闭、先做超时提醒；保留需求的未交付退回需恢复原需求占用；交付、配额、费用分别处理。

**请逐项回答。** 谁确认交接数量？酒店是否实际有确认入口？酒店拒收或少收后是补发还是取消剩余？返回工厂的净品怎样记录？谁可以取消需求或认定责任结案？没有客户回复时只提醒，还是申请自动处理？后者需要何种授权、证据和争议窗口？

**选择与影响。** 人工交接证据可支持一期受控完成；自动确认减少人工动作但影响客户责任，不能因超时就假造客户签名。是否增加酒店确认入口还需检查本期范围，不能顺手扩功能。

**本稿建议。** 先用“正常100件、少2件、拒收、无人确认”四个例子确认结果；不要只确认页面按钮。保持现有关闭自动交付的推荐，待授权后再启用对应策略。

**需要材料／完成证据。** 交接样单、司机与酒店的实际确认方式、差异补发与取消条件、自动启用授权（如采用）。关联 `PD-013/020/028`、`BR-R017/018`、`TASK-09/10`。

<a id="Q-06"></a>
### 问题-06：什么时候形成费用，什么时候付款？

**场景。** 订100件、实际送98件，价格中途变化或订单取消。产品必须能解释应收如何变化，但不能自己确定客户合同的收费条款。

**已有依据。** 当前推荐订单确认形成费用、实交差额调整，确认单据保存价格与规则快照；具体收费时点、价税、舍入及账期／预付的真实选择仍需采纳。未额外包含在线支付、最低消费或月租。

**请逐项回答。** 哪些动作收费？按确认数量还是交付结果调整？价格是否含税，金额在哪一步取整？按月出账还是预付后备货？缺价格时谁补、能否继续？同一客户改价后旧订单用什么版本？少送、取消和返洗分别产生什么费用结果？

**选择与影响。** 账期模式和预付模式有不同的备货门槛；规则可按协议选择，但选择必须明确。新增在线支付或额外收费项目须另做范围和接口评审，不从“付款”一词推导。

**本稿建议。** 财务拿合同和价目表示范至少一笔正常、一笔短交、一笔改单／取消。产品记录业务结果，研发设计费用和调整记录。真实参数未批准时可做模拟，不以支付成功桩开放真实备货。

**需要材料／完成证据。** 去敏合同与价格样本、三类正反算例、结算模式、核准角色和版本生效规则。关联 `PD-015/032`、`TASK-09/11/13`。

<a id="Q-07"></a>
### 问题-07：充值、赠送、信用和退款怎么区分？

**场景。** 一笔订单使用了充值余额、赠送和信用，随后部分取消。退款不能只看当前账户里还有多少钱，也不能把未付的信用当成已支付现金退回。

**已有依据。** 当前推荐保留原资金分摊、双退款限额和在退占用；信用退款先冲原笔未偿本金，已偿部分按原还款来源返还；赠送不兑现。上述商业使用规则仍待授权。

**请逐项回答。** 什么客户可用赠送和信用？按什么顺序扣，哪些费用不能使用赠送？是否允许超额，谁批准、上限和期限？取消时各来源如何退回？退款处理中再次提交怎么办？赠送是否只恢复权益而非退现金？客户的信用已经还了一部分时如何处理？

**选择与影响。** 不同扣款顺序会影响后续可退来源；不能用“余额够就退”代替原交易追踪。参数可以按批准范围设置，但赠送兑现金等变化不能作为普通界面配置偷偷开放。

**本稿建议。** 财务分别走一笔未偿信用、一笔部分偿还和一笔混合支付退款案例，产品确认展示分项，研发沿用主版算法。不能把总退款金额正确当成各资金来源都正确。

**需要材料／完成证据。** 使用资格、扣款顺序、超额授权与退款来源表，正常／重复／在退／部分还款的预期。关联 `PD-033`、`TASK-12`、`UAT-R040/058/059`。

<a id="Q-08"></a>
### 问题-08：赔偿后找回，钱怎么调，布草归谁？

**场景。** 布草被认定丢失，客户只付了部分赔偿，后来又找回。应赔金额、未付金额、已付金额、减免和现金退款不是同一个数。

**已有依据。** 当前推荐先记录找回并待检，按合同确定减免总额，再冲未付、退已结算；产权不自动转移。新旧比例计算基数必须按版本隔离，比例、金额基数和产权依合同批准。

**请逐项回答。** 哪种找回质量可减免？合同里比例乘的是有效应赔额还是已支付额？未付款、付一部分、已付清各怎么处理？谁核准或授权自动核准？退款后产权是否变化？找回品在质量未确认前能否直接再发？

**选择与影响。** 同一个比例作用于不同基数会得到不同金额，不能只回答“按百分之多少退”。减免债务不等于全部退现金，自动核准不等于没有授权。

**本稿建议。** 不在问卷中替客户设定比例。让业务负责人和财务用同一合同分别算三种付款状态，产品据此完善页面和异常提示；有争议时保留案件，不先自动扣退。

**需要材料／完成证据。** 去敏合同条款、计价基数、比例／取整授权、三类付款状态及边界算例、产权处理。关联 `PD-010/034`、`BR-R026`、`TASK-15`。

<a id="Q-09"></a>
### 问题-09：损坏或盘点少了，谁来查和认定？

**场景。** 盘点少10件，可能是正在运输、漏扫、错位或真实丢失；破损也可能是正常磨损。发现异常不应直接等于客户赔偿。

**已有依据。** 当前推荐将报废不可用、责任处置和收费分开；盘点记录差异不直接调账，盘亏不自动客户赔偿；丢失保留最后已知位置，不伪造回厂。返洗计次与是否收费分别处理。

**请逐项回答。** 正常磨损、客户损坏、工厂损坏如何区分、看什么证据？特处和返洗什么情况收费？几天未回仅提示风险，何时进入调查，何时才能认定丢失？空仓确实0件时谁确认？盘点期间移动如何核对？谁能批准报废、调整、减免和赔偿？

**选择与影响。** 提醒、调查、认定和收费是不同阶段；阈值不应由研发随意填一个天数。允许人工处理并不意味着无需记录证据和审批。

**本稿建议。** 先定义异常分类和处理责任，再谈阈值；对每类收集一个真实案例。尚未认定时保留异常和查找，不默认客户承担损失。

**需要材料／完成证据。** 分类依据、证据样例、阈值来源、责任与调整审批流程；正常磨损、错位、在途、确实丢失及零盘点案例。关联 `PD-008/009/029/030/031`、`TASK-14/15/16`。

<a id="Q-10"></a>
### 问题-10：现场用什么设备，断网还要怎样作业？

**场景。** 同样叫“RFID设备”，现场可能是固定读头、安卓手持机或收脏柜；现场操作人关心能否扫、打印、离线补传，研发需要实际协议和样机。

**已有依据。** 一期 RFID 方向已明确；设备范围仍需按首客清单落地。协议、固件和样机未具备时可以模拟，不可标真机通过；现有移动端壳不等于已具备安卓硬件能力。

**请逐项回答。** 首客哪些工位用哪些设备？由人操作还是无人值守？现场断网常见多久，必须继续哪些动作，哪些可以暂停？没有打印机能否继续业务？重启或升级后未上传记录如何处理？故障由谁联系供应商？

**选择与影响。** 只在线操作实现范围较小但影响断网作业；需要离线操作时，必须区分本地已记录与服务端已生效，冲突如何处理也要设计。不能承诺支持所有厂商或任意离线自动放行。

**本稿建议。** 产品描述工位和操作流程；实施向供应商收型号、系统版本、SDK、协议、样机和打印样式；研发确定载体及恢复方案。不要让产品选择底层串口协议或签名算法。

**需要材料／完成证据。** 首客设备清单、现场网络情况、实际协议版本、样机、断网／重启／重传测试结果。关联 `PD-016/036`、`TASK-05/19`。

<a id="Q-11"></a>
### 问题-11：跨日和迟到数据怎么出报表？

**场景（合成）。** 23:58实际收货，00:05联网补传；前一天的报表或账单已经生成。按上传时间算可能改变业务日期，但设备时间也可能不可信。

**已有依据。** 当前推荐受信任发生时间与业务日期口径分开记录，明细实时生效、日单只汇总；迟到数据修订报告，核准后追加调整，不再次改库存或配额。库存时点和期间流量分别统计。

**请逐项回答。** 一个业务日从几点到几点，企业采用哪个时区？跨午夜作业由谁解释归属？迟到多久进入复核？报表生成后和财务核准后分别如何更正？酒店能否看到“已修订”？回收量、返厂复核量和生产量是否在报表中清晰区分？

**选择与影响。** 按发生日统计更接近实际作业，但需要可信时间和修订流程；按接收日直接归类可能改变原口径，不应作为方便实现的默认替代。时区不从程序运行机器推断。

**本稿建议。** 产品、运营和财务共同走一笔跨日、迟到、时钟异常和关账后更正案例，研发负责可信时间、水位和版本实现。

**需要材料／完成证据。** 报表样本、业务日定义、时间可信条件、修订／关账规则与四类预期。关联 `PD-025/035`、`TASK-06/17`。

<a id="Q-12"></a>
### 问题-12：旧测试流程怎样退出？

**场景。** 正式新流程上线了，但旧接口、消息或定时任务还在写测试业务表，或者删除旧订单时把权限、文件和导出的测试一起删了。

**已有依据。** 旧强业务按真实场景重建，不受测试模型限制；平台基础复用，旧测试数据不进正式期初。实施前仍需核对当前代码、调用链、迁移历史和恢复任务，不直接改写已执行迁移。

**产品需要回答。** 哪些旧页面和流程还被用于演示？谁会受影响？新流程必须具备哪些可操作能力才允许切换？试点人员何时采用正式入口？这些是业务沟通问题，不要求产品评审DDL。

**研发需要交付。** 旧类／表／接口／消息／任务及调用方清单、新旧切换边界、历史文件与导出未决操作处置、正式契约版本、恢复验证；不得新旧双写或保留暗中的旧逻辑兜底。

**本稿建议。** 产品只确认可见业务影响与验收场景，研发承担技术清单和方案。按正式切片逐批退出旧链，不先清空业务目录，也不把全部旧数据迁移当成必需工作。

**需要材料／完成证据。** 实际代码基线、调用方和迁移记录、旧入口退出证明、基础能力回归及恢复证据。关联 `TASK-00/18/20/21` 和原问题-12；不是产品业务知识不足导致的阻塞。

<a id="Q-13"></a>
### 问题-13：参考资料哪些能作为依据？

**场景。** 参考系统页面显示“自动完成”或“退款比例”，但没有说明后台规则。仅看界面不能知道真实计算与授权条件。

**已有依据。** 原问题表记录部分外部PRD尚缺正式归档；已有历史只读观察不等于完整算法证据，也不允许推断未见的后台行为。

**请逐项回答。** 资料由谁提供、什么日期和版本？可否在项目内保存去敏副本？哪些是文字明确写出，哪些只是截图或口头说明？当前产品方案究竟采纳了哪一项，还是仅参考布局？

**选择与影响。** 可以只参考交互，并独立设计、批准本项目规则；也可以补完整资料后扩大引用。不能把“竞品这么做”作为收费、身份或退款的充分依据。

**本稿建议。** 标明“原文事实／界面观察／设计推断”，按范围记录。缺少外部资料不必阻断已明确的现有功能，但不再扩大未经证实的引用。

**需要材料／完成证据。** 去敏副本、提供方、日期版本、允许使用范围，以及具体采纳或未采纳的结论。关联原问题-13和 `R1.1-UI` 来源记录；不收集账号密码或真实客户隐私。

<a id="Q-14"></a>
### 问题-14：谁完善，谁确认，谁验收？

**场景。** 一份表被回复“没问题”，但没有人补合同、没有规则版本，也没有实际验收记录。讨论结束不能自动成为正式批准。

**已有依据。** 当前多数责任只有角色，没有具体人员；问题按总表各自的关闭条件补证据。规则选择类问题完成授权采纳并回写主版后，可以关闭对应选择，不必等全部代码开发完成；任务完成、目标环境验收和商业启用仍需分别留证，不能从问题关闭推导。

**请逐项回答。** 谁记录现场事实？谁有权批准该经营结果？谁负责技术方案？谁执行测试？试点用户是谁？资料放哪里，哪些内容可去敏共享？正常和异常案例由谁共同核对？

**选择与影响。** 一人可兼任多角色，但应注明以哪个角色作哪种确认；产品整理记录不等于财务批准，研发自测也不等于客户验收。

**本稿建议。** 先给首批任务明确实际人员和证据位置，再逐批扩展。只要求对相关范围负责，不让某人被动签认整包。没有权限或资料的人可以明确写“待调查／需某角色确认”。

**需要材料／完成证据。** 一张实际分工表、决策记录、前后端提交、环境、用例执行结果和验收人；没有证据时保持未完成。关联原问题-14及受影响任务。

## 四、每个子问题怎样填写

复制下面的小卡即可；不创建第二套FR/BR编号，不重复登记主版算法。

| 字段 | 填写内容 |
|---|---|
| 原问题与子问题 | 例如：问题-03 / 03-01 |
| 本次适用范围 | 工厂、客户／协议、品项、期次及生效范围；未知写待查 |
| 当前理解 | 用自己的话描述现场怎么做 |
| 实际场景和证据 | 去敏单据、操作说明、来源人、日期；合成例子必须注明 |
| 现有推荐及出处 | 对应PD/BR，不把推荐写成已确认 |
| 暂选结论 | 采用推荐／采用其他方案（说明）／本期不启用／不清楚待调查 |
| 原因及例外 | 为什么适合本次范围，哪些客户或情况不适用 |
| 正常案例预期 | 动作前是什么、做了什么、动作后是什么 |
| 异常案例预期 | 缺证据、少收、重复、撤销等发生时怎么处理 |
| 尚缺信息与调查对象 | 谁提供什么资料，哪些任务受影响 |
| 建议记录人／确认角色 | 实际姓名待指定，经营与技术确认分开 |
| 正式采纳记录 | 采纳人权限、日期、规则版本及主版位置；未批准保持空缺并标明待确认 |
| 关联交付与验收 | TASK、UAT、实际代码／文档提交及环境证据 |

问题可以“部分明确、局部受阻”。若只知道正常情况，就先记录正常情况，不编造异常答案，也不能因此把整个问题关闭。

## 五、产品不熟悉业务时，怎样开讨论会

先请现场人员复述最近一次真实作业，产品用本手册提问并记录；然后把已经存在的推荐方案和不同选择的后果摆出来，避免无依据地让对方从空白开始设计系统。能取得去敏单据就核对，不能取得时用合成例子，并标明证据等级。

每次只围绕首批任务讨论相关问题。建议先明确首批范围和责任人，再按客户服务、资产期初、收货配额、交付及财务的依赖逐步推进；研发的身份、设备和替换核对可以并行。

讨论输出不是一句“支持”，而是“适用范围＋选定动作＋证据要求＋正常／异常结果＋授权人”。收费、信用、退款、赔偿和客户责任由有权限的业务／财务人员确认；产品和AI负责整理与提出建议，不代替授权。

一个可以直接发给产品的说明：

> 这份清单不是让你独自回答所有行业细节。我们已经整理了现有推荐方案、实际场景和需要确认的问题，你可以逐项补充目前了解的做法；不确定的写“待调查”，再一起找运营、司机、仓管、财务或客户核对。我们重点确认业务结果和异常处理，技术方案由研发负责，经营条款由对应授权人确认。最终只把有依据、适用范围明确的结论写回正式规则。
