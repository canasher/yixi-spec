# 文档编写与维护约定

适用于本仓库。业务规则是否生效，以对应采纳记录和适用版本为准；本约定只管理文档。返回[首页](../README.md)。

## 组织与命名

业务目录及文档名称使用明确中文，例如“客户资金”“业务规则.md”；不用“新文档”“最终版”“其他说明”。`README.md`、`AGENTS.md` 及 `.gitattributes` 保留工具名称。编号、API 标识符及文件格式扩展名不翻译。新增业务先建实际入口，有内容时再拆文档，不复制整套空模板。

跨业务的工程边界放[全局规范](../全局规范/系统边界与共用约定.md)；租洗跨模块的规则、模型与任务放[共用规范](../业务/租洗/共用规范/README.md)；模块目录负责本模块入口及后续专属内容。共用内容只留一个维护位置，模块通过编号和相对链接引用。源文件、历史记录与当前规范分开，禁止把旧设计当最新说明。

## 三种状态分别记录

| 维度 | 可用值与判断 |
|---|---|
| 文档 / 规则状态 | 草案 → 待确认 → 已确认；已废弃必须注明替代文档或决定、日期和适用终止范围，保留历史编号 |
| 实施范围 | 当前一期 / 未来预留 / 待确认；“预留结构”不等于实现完整业务 |
| 实现 / 验收状态 | 未开始、进行中、受阻、已实现、测试环境通过、目标环境已验收；商业启用另记，不从文档状态推导 |

R1.1 历史用语“推荐待采纳”对应待确认；“已明确方向”只确认其列明范围；“来源明确”只表明来源可查，不能映射为已确认。现有 TASK 中 `NOT_STARTED / IN_PROGRESS / BLOCKED / IMPLEMENTED / VERIFIED_IN_TEST / ACCEPTED_IN_TARGET` 与上表实现状态一一对应。UAT 当前值“未执行”保持不变，执行后记录通过、失败或受阻及证据。

一份文档内可以同时含已确认方向和待确认规则，必须按条目标识。主文档版本沿用 R1.1，本次目录迁移不会将它升级为业务批准版本。已实现至少关联实际代码提交及验证结果；目标环境已验收还需环境、日期、用例结果和验收责任人，编译通过不够。

## 六类文档的最小信息

| 类型 | 必需信息 |
|---|---|
| 产品需求 | 背景/目标用户、场景、当前及排除范围、FR、验收目标和来源 |
| 业务规则 | BR、前置、状态/数据变化、异常/重复/并发、撤销或更正、算例、来源和 PD |
| 领域设计 | 概念、关系与职责、权威事实、事务/API/权限边界、关联 FR/BR、当前事实与目标设计的区别 |
| 实施任务 | TASK、依赖、FR/BR/UAT、前后端交付、不做什么、开工门槛和完成证据 |
| 验收用例 | UAT、关联需求/规则、环境/初始数据、步骤、预期、类型、执行状态和证据 |
| 决策记录 | PD 或记录 ID、问题/备选、选择与原因、状态/采纳人/日期、影响范围、替代关系及关联任务用例 |

FR 与 UAT 的关系集中在[需求索引](../业务/租洗/结构化数据/需求索引.json)和模块页；用例卡片保持 BR 引用，不再复制一份完整 FR 映射。文档头建议写“状态、版本/日期、适用范围、维护角色、关联入口”，尚未指定人员时写“待指定”，不能编造负责人或批准日期。

## 编号与追踪

保留 `FR-Rxxx`、`BR-Rxxx`、`TASK-xx`、`UAT-Rxxx`、`PD-xxx`、`SRC-xxx`、`DEP-xx`。不因改名重编，不重用已废弃编号；新编号在对应索引续增并检查唯一。尚无编号体系的新业务先说明命名空间，不挤用租洗编号。

正文中的旧章节简称仍有“01～06”：依次对应产品需求、业务规则、领域与技术设计、实施计划、验收用例、决策记录；章节内容未重新编号。新导航使用中文文件链接及稳定显式锚点，少依赖自动生成的标题锚点。跨仓链接用完整 GitHub 地址；验收证据和基线用固定提交，不能依赖本机绝对路径。

Markdown 是维护主版；JSON 是可校验的索引、追踪和合成数据，不能单独改变规则。模板不是第二份主版。暂不建设额外文档网站或生成流水线。

## 大模型执行与过程记录

采用[大模型研发流程](../大模型研发流程/README.md)管理自动读取、拆解、实施、验证和交接；沿用本文件的规则、范围、实现/验收状态，不新增平行的 TASK 状态机。人负责必要事实、授权与风险决策，AI 可以在明确授权内执行相应研发职责；这一分工不把“待采纳”变成“默认同意”。

每个切片只保留一份执行记录，放主 Issue/PR 或受控文件；[JSON模板](../大模型研发流程/模板/任务执行记录.json)是可检查快照，不重复维护业务规则。重要结论回写唯一主版，运行日志留在适当证据存储。过程变化不自动改业务版本、TASK/UAT 状态或客户启用配置。

[记录检查器](../校验/检查执行记录.py)独立于原文档检查器；只检查声明的结构、版本与证据字段，不能证明实际授权、执行或上线安全。模板故意不满足开工门槛；过程约定不等于已配置分支保护、CI 或持续执行器。

## 一次变更如何闭环

1. 明确问题、期次、关联编号、当前采纳状态及影响的在途/已结算事实。只有链接或错字变化时直接修正并说明，无需新增业务决策。
2. 需求或规则变化先登记决策或待确认问题，说明备选、建议及影响；有授权后记录采纳人、日期、适用客户/规则版本和启用条件。
3. 修改唯一主版，按影响同步 FR/BR、领域设计、TASK、UAT 与 JSON；更新模块入口和范围追踪。保持验收预期与最终方案一致。
4. 开发切片登记本规范仓提交、两代码仓提交/拉取请求、接口契约版本；文档主版与代码不同时完成时明确差距和阻断功能。
5. 运行文档检查并审阅差异。通过提交或拉取请求评审；产品/业务负责人确认经营结果，研发负责人确认技术契约，测试负责人确认可验证性。具体人员待项目指定，不由整理者代签。
6. 实际实现及验收完成后补证据、变更状态；被替代规则保留引用与退出范围，不重算旧业务事实。

任务开工至少具备已确定的切片范围、相关规则版本、设计接口、依赖及 UAT 预期；缺少的商业参数可以允许计算器/模拟开发，但必须阻止对应真实扣退行为。完成标准以[实施计划](../业务/租洗/共用规范/实施计划.md)任务卡为准，不用“页面能打开”替代端到端交付。

## 冲突、校验与历史资料

仓库安全/工程约束由目标代码仓当前 `AGENTS.md` 与已接受 ADR 管理；产品范围与业务规则由本仓主版及采纳记录管理。两者冲突时登记影响并协调，不能用某一类文档覆盖另一类的权限。推荐方案与批准结论不一致时，保留推荐历史，按明确版本记录已采纳结果。

待确认清单只登记问题、来源、影响、责任角色和关闭条件；结果回写决策及相关主版，再关闭问题。只阻断确实依赖该决定的切片。未来需求留在[后续范围](../业务/租洗/后续范围.md)，不算本期未完成功能。

执行 `python3 校验/检查文档.py`，检查文件命名、本地链接/锚点、编号关系、任务依赖、源文件 SHA、Markdown/JSON 同步及数值算例；再执行 `git diff --check`（已暂存时加 `git diff --cached --check`）。脚本只读，不访问网站，不代替业务测试。外链可用性需引用时另查，历史提交链接表示当时证据。

原始资料保留来源编号、原文件名及 SHA；新版本新增来源记录，不覆盖旧原件。历史 Markdown 的中文可阅读副本只修复内部文件链接，原始字节保存在归档包并校验。过期 HTML/Excel 不作为当前规范，不在其中维护业务规则。
