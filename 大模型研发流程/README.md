# 大模型主导的研发流程

> 版本：流程约定 1.0；日期：2026-10-02。
> 适用：以大模型完成主要分析、设计、编码、测试、审查和文档维护，人提供现场事实、授权及风险决策的项目。
> 边界：这是工作协议及轻量检查工具，不是 CMMI 评估结论，也不是已经运行的无人值守研发平台。业务规则版本仍沿用各自采纳记录，不随本流程升级。
> 返回：[仓库首页](../README.md) · [AI 工作约定](../AGENTS.md)。

## 一句话工作方式

人给目标和允许范围，AI 自行读取规范与源码、拆分任务、实施、验证、审查并交付证据；只有真实事实缺失、越过授权边界或无法消解的冲突，才请求人的最小决策。**减少的是人工操作，不是验证、权限或业务责任。**

```text
目标输入 → 定位任务与基线 → 判断可执行范围 → 小切片实现
              │                    │                 ↓
              └─ 缺口调查 ← 最小人工决策       验证 → 审查 → 交付
                                      失败 ↖ 修复      ↓
                               验收 → 发布准备 → 授权部署／启用
```

上述是工作步骤，不新增一套 TASK 状态。任务、规则、UAT 和商业启用继续按[文档维护约定](../协作指南/文档维护约定.md)分别登记。已交付代码、目标环境已验收、已部署、商业已启用不是同一个结论。

## 按需要阅读，不要求人维护七套表

| 要解决的问题 | 唯一过程入口 |
|---|---|
| 只给一个 TASK 或业务目标，AI 怎样开始 | [任务启动协议](任务启动协议.md) |
| 哪些自己做，哪些记录，哪些必须询问 | [自主决策边界](自主决策边界.md) |
| 三仓版本、并行修改和中断恢复怎么处理 | [规范与代码基线](规范与代码基线.md) |
| 什么证据允许推进，失败时怎么办 | [开发与验证门禁](开发与验证门禁.md) |
| 人不熟悉行业时，怎样少问而问清楚 | [人工确认与升级](人工确认与升级.md) |
| 交付报告、执行记录和复盘怎样落地 | [交付与证据规范](交付与证据规范.md) |

每个切片只维护**一份执行记录**，可放在主 Issue/PR 或受控文件中。规范正文负责长期规则；Issue/PR 负责当次进度、证据和讨论；JSON 是可检查快照，不成为第二份任务或业务主版。不预建大量空任务、会议记录或审批表。

## 当前采用的自主程度

在本次任务授权内，AI 可以连续完成读取、计划、允许的实现、测试修复、文档同步和提交准备，不逐函数请示。已获明确提交授权时按仓库规则提交分支/PR；合入、发布、生产迁移和商业启用分别核对授权，不能由“开始开发”推导。

已有明确规则直接实现；缺少低风险实现细节按既有架构补齐并留下理由。**“推荐待采纳”仍不是已批准**。存在未决经营规则时，先做不依赖它的工作；需要验证方案可做隔离模拟，但不得把模拟入口接入真实业务。详见[自主决策边界](自主决策边界.md)。

人无需逐行审查所有代码。低风险且已授权的变更可依赖确定性检查与 AI 审查；高风险结论仍由对应授权人确认。同一模型换会话审查能补充视角，但不是绝对独立，也不能代替测试。

## 最小落地与尚未实现的能力

本轮提供过程文档、[执行记录模板](模板/任务执行记录.json)和[只读记录检查器](../校验/检查执行记录.py)。检查器只查结构及所声明状态的一致性，不执行记录里的命令，不读取密钥，不自动改状态，也不证明证据真实。

GitHub 分支保护、必需检查、独立审查任务、隔离测试环境、真机接入和持续调度，需在对应仓库及执行环境实际配置后才算具备。本流程不宣称已经配置，也不自动授予发布权限。本轮检查边界见[建设记录](../维护记录/大模型研发流程建设记录.md)。

先用一个已满足开工条件的低风险切片试行，记录返工原因和人工介入点，再把重复错误转成可重复检查；不以 token、代码行数或 PR 数量替代质量。
