# 规范与代码基线

> 流程约定 1.0；基线用于重现和恢复，不是复制三套规范。
> 返回：[流程首页](README.md)。

## 固定输入，区分实现结果

每个执行记录写明规范仓及本次涉及代码仓的完整 commit SHA、分支/PR、工作区状态，以及相关 AGENTS/ADR 的位置。不涉及的仓库写不适用原因，不能伪造一个“最新提交”。规范内容版本与 Git 提交不是同一层：规则集版本控制业务语义，commit 固定具体文档或源码。

输入基线是开工时参考的版本；输出候选版本是实际被验证的改动。运行测试后又修改了代码、契约、配置或测试，原证据不自动覆盖新版本，需重跑受影响项。记录可写在 Issue/PR，避免为了把自身提交号写入文件而产生无限自引用提交。

## 三仓协作而非原子提交

`yixi-spec` 管业务规则与采纳，`yixi-saas` 管后端/迁移/实际契约，`yixi-web` 管前端和生成客户端。执行记录列出同一切片的规范提交、后端提交、前端提交、OpenAPI 版本/哈希、数据库迁移和终端版本（适用时）。代码仓约束仍以其当前 AGENTS 和已接受 ADR 为准。

三仓没有天然原子合入。先确定兼容窗口与上线次序；生产方发布正式接口契约，消费者基于该契约生成并验证 Client，不能手改生成代码掩盖漂移。正式需求需要前后端时，单仓完成不等于整体完成。可采用明确版本兼容与未启用状态隔离，但不建设长期旧测试业务双写兜底。

中途发现业务规则必须变更：登记影响 → 获得必要采纳 → 更新唯一主版及关联数据 → 形成新基线 → 重新检查受影响任务。不能只追随变化中的 main，也不能长期停留旧基线而不披露。配额/价格等已存快照的旧事实按正式变更规则处理，不静默重算历史。

## 分支与并行代理

新工作分支使用 `codex/` 前缀；保留原有未提交修改。不执行强推、重置他人工作区或顺手清理无关文件。合入前重新读取目标分支；远端变化时重新比较、协调并复验，不能覆盖他人提交。

同一切片指定一个协调执行者，子代理可以负责后端、前端或审查，但各自有文件范围、基线、输入输出和验证责任。共享契约由明确角色串行维护；同一路径冲突先协调。没有可用子代理时，单模型可以分阶段处理，但报告不得声称进行了多代理独立审查。

旧订单、库存、消费者和定时任务的退役沿既有替换计划逐批处理；已执行 Flyway 历史不重写。新迁移、权限和文件/导出回归必须保持可追溯。此处只规定过程，不新增跨库事务或新的业务权威。

## 断点续做

中断、换会话或更换模型前留下：目标/授权、三仓基线、分支及当前差异、已完成动作、未完成验证、阻塞和决策、失败尝试、下一条安全动作、禁止重放的副作用。详细格式见[交付与证据规范](交付与证据规范.md)。

恢复时重新核对分支、工作区、权限、未决事项与输出文件，不盲信摘要中的“已提交”“测试通过”。对外部写入结果未知，先读取远端/查原业务号确认，不创建重复提交、工单、退款或设备命令。只重跑明确可安全重试的动作。

## 合入与发布不是同一授权

提交分支/PR、合入主干、部署、生产迁移、开启收费功能分别核对权限。默认交付可审阅分支/PR，不把“开发完成”理解成发布。用户明确要求直接提交主干且仓库规则允许时，可以在复验远端及差异后非强制更新；不得绕过已配置保护。

无法取得完整仓库或必需测试环境时，可以交付明确标注限制的草案/分支；不能填写“全量检查通过”。是否允许合入由[门禁](开发与验证门禁.md)和实际授权决定，本流程不自动创建豁免。
