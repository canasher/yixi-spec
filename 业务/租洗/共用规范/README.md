## 1. 本包交付什么

R1.1核心修订处理评审前三项：未交付退回后补发预占、分次退款限额与在退占用、信用还款后退款和部分赔偿找回。规则主版见02§5.1、§6.1～6.3；技术契约见03§6.4、§9.1～9.3；原70个UAT编号下补充子场景，不扩大一期菜单范围。回购新推荐以有效应赔额确定减免总额，旧已付基数策略按明确历史版本隔离；详见06的R1.1兼容说明。

交互补充见[01§7](产品需求.md#UI-COMMON)：客户/线路作业配置、发货与差异追溯、配额来源、账单、资金退款、赔偿回购六类页面。用户已采纳文档修改；04§2.1登记任务映射，05及JSON同步10个原UAT的页面子场景。核心算法和一期76组范围不变，真实业务验收仍未执行。

架构补充已对照yixi-saas与yixi-web源码：四端载体见[03§12](领域与技术设计.md#ARCH-WEB)，全部25个FR的前后端模块、现状缺口、接口/权限和任务/验收见[03§13](领域与技术设计.md#ARCH-MAP)，OpenAPI/Client接入见[03§14](领域与技术设计.md#ARCH-CONTRACT)。04及任务JSON同步6张任务卡，05及用例JSON扩充6个原UAT；两仓业务源码未修改。

最新实施基线：用户确认现有订单、库存等强业务只是初步测试代码，须按真实场景替换。[03§1.1](领域与技术设计.md#REPLACE-BASELINE)区分平台复用、业务重建与适配迁移，[04§2.3](实施计划.md#REPLACE-PLAN)明确分批替换和退出；该轮同步9张任务卡及4个原UAT。旧测试数据不导入正式业务，不为旧业务建立双写或长期兼容层；文件/导出/权限基础回归继续保留。

本版承接原《产品需求 V1.1》《领域模型 V1.2》，包含完整原清单映射、逐动作规则、目标模型与首批接口、任务卡、合成算例和决策记录。旧稿在[资料来源](../资料来源/README.md)中归档；旧的一期范围不再作为新开发依据。2026-10-02迁入yixi-spec后增加按业务阅读的入口，R1.1经营规则、功能期次和验收状态不变。

**当前是设计评审版，不是产品已全部批准、代码已完成或真实设备已验收的证明。** 本版给出明确推荐方案，避免所有细节都悬空；项目负责人可逐任务采纳低风险技术/业务默认规则。收费、回购、授信及客户责任条款必须有业务授权后才对真实客户生效。

## 3. 来源、规则状态与优先级

来源类型不等于采纳状态：`U`为用户明确方向；`S1～S3`为产品原材料；`S4～S6`为上一轮设计/评审；`G1`为前轮后端入口文档读取，`G2`为本次两仓源码定向核对；`D`为补充的推荐设计。没有原文支持的算法或字段必须标为D，不能伪装成行业统一标准。

| 状态 | 允许的后续动作 |
|---|---|
| 已明确方向 | 本次用户确定先租洗后普洗、结构预留、形成共享文档；可据此限定范围 |
| 来源明确 | 原资料如此描述，但仍需确认适用一期及是否与其他来源冲突 |
| 推荐待采纳 | 本包已给出一个可执行默认方案；任务开始前由负责人采纳对应规则版本，不必逐字段问产品 |
| 商业启用门槛 | 可开发计算、模拟及结构；真实扣费/退款/超额信用须批准参数和算法后启用 |
| 后续预留 | 保持兼容或拒绝路径，不创建空业务模块，不开真实入口 |
| 已实现/已验收 | 只能以实际提交、环境、测试/业务验收证据登记；本包没有此类新增完成声明 |

冲突分维度处理：仓库安全/模块边界由AGENTS和已接受ADR约束；一期范围由用户方向与经采纳的S1范围决定；具体业务规则由02及06的生效记录决定；代码只说明当前实现，不自动决定未来产品。业务想突破既有IAM/文件协议，先做专项设计与ADR，不能用PRD一段话覆盖安全约束。

## 4. 本版核心取舍

一期以租洗RFID、收发、资产运营、客户财务和四端查询/操作为目标。完整生产路线/MES不前置，一期采用“工作台产出确认+独立打扎事实”的推荐方案。服务模式、所有权、追踪方式、客户持有、库存池与计费来源分离，为普洗留结构，不开发普洗收发页面或重量权威库存。

原清单的一期76组均保留在映射中；依赖功能另列DEP，不把它们冒充原产品功能组。酒店下单、在线支付、自动下单、集团/前置仓、商城、采购、完整载具管理不因原资料有示意图就全部前移。

## 5. 使用与变更

每个实施任务必须记录本次commit、采纳的规则版本、商业参数批准状态、允许范围和验收编号。修改顺序为：06留决策 → 02改规则 → 01调整用户流程/范围 → 03调整契约 → 04改任务 → 05改预期；引用编号尽量不复制规则全文。允许不同任务并行，但共享唯一键、资金/配额算法和跨端状态必须同版本。

Markdown是维护主版，[结构化数据](../结构化数据/README.md)保存同步索引与算例；此后统一在yixi-spec维护，通过规范提交与代码提交关联，不再向两个代码仓库复制一套文档。全局约束、租洗共用规范及模块入口的维护职责见[文档维护约定](../../../协作指南/文档维护约定.md)。文档导入本身不表示方案全部批准。

原包HTML、导出Excel/CSV及根文件清单仍为R1历史视图，未包含R1.1补充，本次没有导入为当前规范。历史验证见[历史校验记录](../资料来源/历史校验记录.md)，本次迁移检查见[本次校验记录](../../../维护记录/本次校验记录.md)。

## 6. 第一次交给Codex的任务

只执行TASK-00和TASK-01的资料整理部分：只读核对当前提交和既有接口/迁移，给出差异、冲突及首批规则采纳清单。不要全量生成Java/SQL，不改生产配置，不调用真实支付/设备。首个业务开发建议从TASK-03主数据、07配额底座再到04资产期初切片开始，身份相关修改必须遵守TASK-02门槛。

G2记录两仓现状，G3补充用户确认的测试业务定位和关联引用；TASK-00据此完成替换清单，不重新论证旧测试模型是否适用。酒店/设备身份、正式业务契约与Client、附件/导出适配及安卓载体为开工/联调项；旧测试接口不必先补齐再替换，见04§2.2/2.3。

任务交接固定包含：实际修改文件、关联BR/UAT、数据库变化、兼容影响、执行命令、真实结果、未验证项、回滚/恢复方式。禁止把此包预期算例当成已通过测试，禁止虚构CI结果。
