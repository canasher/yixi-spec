# 业务规范仓库（yixi-spec）

本仓库是 `yixi-saas` 后端与 `yixi-web` 前端的统一业务文档入口，供产品、研发、测试和 AI 共同使用。业务范围、规则、设计、实施任务和验收依据在这里维护；代码、实际接口契约和运行证据仍由对应代码仓库管理，通过提交或拉取请求关联。

**当前业务为租洗一期，来源版本为 R1.1 设计评审版。目录整理不表示全部方案已经批准，也不表示业务已经实现。** 当前 70 个验收用例均未执行；商业参数、身份接入和设备条件见[待确认事项](维护记录/待确认事项.md)。

按业务选目录，再沿模块页中的六类资料往下读。现有六份主文档涉及同一条租洗业务链，保留在“共用规范”集中维护；模块页提供具体编号、章节、任务分工和验收入口，不复制算法。后续模块内容增长时，可将专属章节迁入对应业务目录，并同步引用；不必给每个模块预建六份空文件。

## 六类内容如何关联

| 类型 | 回答的问题 | 当前主版 |
|---|---|---|
| 产品需求（FR） | 谁在什么场景下，需要做什么；哪期做 | [产品需求](业务/租洗/共用规范/产品需求.md) |
| 业务规则（BR） | 怎样流转，哪些约束、异常与边界必须处理 | [业务规则](业务/租洗/共用规范/业务规则.md) |
| 领域设计 | 有哪些业务概念，谁负责事实、事务和接口 | [领域与技术设计](业务/租洗/共用规范/领域与技术设计.md) |
| 实施任务（TASK） | 前后端做什么、依赖什么、交付什么证据 | [实施计划](业务/租洗/共用规范/实施计划.md) |
| 验收用例（UAT） | 用什么数据和步骤判断通过 | [验收用例](业务/租洗/共用规范/验收用例.md) |
| 决策记录（PD） | 为何选择当前方案，哪些尚待采纳 | [决策记录](业务/租洗/共用规范/决策记录.md) |

追踪链为“来源 → FR → BR → 领域设计 → TASK → UAT”；PD 关联其中的重要取舍。各模块页是这条链的可点击入口，[范围追踪数据](业务/租洗/结构化数据/范围追踪.json)保留原清单单元格及期次。编号不会因文件迁移而改变。

## 当前实施边界

一期保留原清单 76 组功能，以租洗 RFID、四端收发作业、资产运营及客户财务为目标。原二期 38 组、三期 9 组保持后续范围；普洗仅保留结构及拒绝路径，自动下单等未获范围变更前不能进入一期交付。

用户已明确：现有订单、库存及关联强业务只是初步测试实现，正式业务按真实场景重建替换；复用 IAM、企业切库、统一返回、文件及导出等平台基础。代码仓中的菜单预览、测试数据和旧接口都不是新业务已完成的证据。详细边界见[替换基线](业务/租洗/共用规范/领域与技术设计.md#REPLACE-BASELINE)。

## 怎样维护

修改主版时，同步关联编号、结构化数据、模块导航及验收预期；在提交或拉取请求中写明原因、范围、状态及验证结果。确认业务方案需要可追溯的采纳人、日期和适用范围；合并文档不自动批准商业启用。开发提交应关联本仓库的具体提交及 FR/BR/TASK/UAT，避免始终引用变化中的 `main`。

在仓库根目录执行：

```bash
python3 校验/检查文档.py
git diff --check
```

检查只证明文档、链接、来源、追踪和数值算例一致，不证明后端、前端、数据库、支付或真机验收通过。原文档包的旧 HTML/Excel 阅读导出没有导入为当前视图，详见[迁移说明](维护记录/迁移整理说明.md)。
